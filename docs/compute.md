# Compute Engine (`compute.googleapis.com` v1)

`--services compute` (#1936) serves the VPC networking part of the Compute Engine API in the CLI process: networks (auto and custom mode), subnetworks with their secondary ranges, firewall rules, routes, global and regional addresses, the global, regional and zonal operations, and the regions and zones. It is JSON under `/compute/v1/` on `--port-compute` (default `9031`), as Google's paths are, plus the batch endpoint `/batch/compute/v1` that gcloud sends its calls to. Compatibility status, method by method, is in [compatibility.md](compatibility.md#compute-engine-vpc-networking--computegoogleapiscom-v1).

VM instances, disks, snapshots, machine types and the public images are served too (#1963); see [VM instances](#vm-instances) below.

## What a network is here

A network, its subnets, its firewall rules and its routes are records, validated as Google validates them, that the other services check their own network fields against. Between VM instances they also carry traffic, with the firewall rules enforced: see [VM networking and firewall rules](#vm-networking-and-firewall-rules). For the other services' resources nothing is routed:

| Service | With `compute` | Without it |
|---|---|---|
| Memorystore for Redis | `authorized_network` must exist; a `reserved_ip_range` must not overlap a subnet or an allocated range of it (a range chosen for the instance is moved off them); with `PRIVATE_SERVICE_ACCESS`, a range name must be an allocated range of the network | any network and range |
| Redis Cluster, Memorystore for Valkey | each PSC network must exist | any network |
| Kubernetes Engine | the cluster's network must exist, and its subnetwork be that network's in the cluster's region | any network |
| Cloud SQL | `settings.ipConfiguration.privateNetwork` must exist, and `allocatedIpRange` be one of its allocated ranges | any network |

Every project starts with its `default` network, as a project with the Compute Engine API enabled does: auto mode, one `/20` subnet per region (the documented auto mode ranges, `10.128.0.0/20` in `us-central1`), the `default-allow-internal`, `-ssh`, `-rdp` and `-icmp` firewall rules, and the default route to the internet. Delete it and it is not made again.

Every insert, patch and delete completes at once and answers with a `DONE` operation (`compute#operation`), global, regional or zonal as Google scopes it; the clients' `Wait` returns at once.

External addresses are chosen from documentation ranges (`203.0.113.0/24` regional, `198.51.100.0/24` global), since no address here is reachable from the internet. Internal addresses are chosen from their subnet's primary range, skipping the four addresses Google reserves.

## Ports

Compute Engine is an API of its own, so it has a port of its own rather than sharing the Kubernetes Engine API's. The Kubernetes Engine port has long answered the one Compute call Terraform's `google_container_node_pool` makes (`instanceGroupManagers.get`, for a pool's size). With `compute` enabled, the Compute port answers it too, from the same node pools, and `cloudburrow terraform` points `compute_custom_endpoint` at the Compute port; without `compute`, nothing changes.

## Clients

```sh
cloudburrow up --services compute
eval "$(cloudburrow env)"            # CLOUDBURROW_COMPUTE_ENDPOINT, CLOUDSDK_API_ENDPOINT_OVERRIDES_COMPUTE
gcloud compute networks create vpc --subnet-mode custom
gcloud compute networks subnets create nodes --network vpc --region us-central1 --range 10.0.0.0/24 \
    --secondary-range pods=10.4.0.0/16
gcloud compute addresses create db --region us-central1 --subnet nodes
```

The Go client takes the endpoint with its scheme:

```go
c, err := compute.NewNetworksRESTClient(ctx,
    option.WithEndpoint("http://"+os.Getenv("CLOUDBURROW_COMPUTE_ENDPOINT")),
    option.WithoutAuthentication())
```

Terraform's `google_compute_network` and `google_compute_subnetwork` run through `cloudburrow terraform`.

## VM instances

The design (#1963, option A): **a VM is a systemd container** in the instance's kind cluster, a privileged pod booting `/sbin/init`, and the API (instances, disks, snapshots, images, machine types, zonal operations) sits on a backend interface (`compute.VMBackend`) so a microVM backend can be added later on Linux hosts with `/dev/kvm`. A container has no kernel of its own, so what needs one is refused or documented, never faked.

| Google | Here |
|---|---|
| Public images `debian-12`, `ubuntu-2404-lts` (`-amd64`, `-arm64`), `rocky-linux-9` | A container image of the same distribution, built on this machine at first use from the official image pinned by digest, plus the distribution's systemd, OpenSSH, sudo and curl packages and the guest scripts in `internal/service/compute/guest` (no code of them is linked into CloudBurrow). Tagged `cloudburrow-vm-FAMILY:HASH` |
| Custom images (`images.insert` from a disk, a snapshot or an image; families, `deprecate`) | A copy of the source's files in a PersistentVolumeClaim, from which disks are seeded as from a public image (#2139); `rawDisk` imports a Cloud Storage file (a `.tar.gz` of a single `disk.raw`, as [import-existing-image](https://docs.cloud.google.com/compute/docs/import/import-existing-image) documents): its largest Linux partition (GPT, MBR, or a whole-disk ext4 or XFS) is loop-mounted read-only in a privileged pod and its `/etc`, `/home`, `/opt`, `/root`, `/srv`, `/usr` and `/var` copied into the image's claim, the boot-disk layout every disk here has, so an instance made from it runs the imported system's files under the container of its `os-release` distribution (Debian when it names none served); the kernel, boot loader and other partitions are not used, as the container shares the host's kernel. A disk without `/etc` and `/usr` fails the import. Google's errors: a source outside Cloud Storage 400, a missing object `NOT_FOUND`, an archive that is not a gzip tar of one `disk.raw` `The tar archive is not a valid image.` (both on the operation); without Cloud Storage served, 501. A virtual disk in Cloud Storage (`rawDisk.source` naming a `.vmdk`, `.vhd` or `.vhdx`, as compute/docs/import/importing-virtual-disks imports one) is converted to its raw disk by `internal/vdisk`, CloudBurrow's own converter written from VMware's and Microsoft's format specifications (no qemu-img): VMDK monolithicSparse and streamOptimized, VHD fixed and dynamic, VHDX; it is then imported as a `disk.raw` is. Differencing disks, VHDX with an unreplayed log and VMDKs whose data is in other files are refused 400 with the reason ("only monolithic VMDK files are supported"). Google's own route for a virtual disk, VM Migration's `imageImports`, is not served (#2139) |
| `cos-stable`, Windows, Fedora CoreOS, licensed images | 501, with the reason |
| Instance templates, managed and unmanaged instance groups, machine images (#2139) | Served as Google documents them: a managed group makes its VMs from its template, named `BASE_INSTANCE_NAME-xxxx`, and resizes, recreates, starts and stops them; setInstanceTemplate changes the template of new VMs only, and recreateInstances re-makes a VM of another template from the current one, by the same name. A regional group (`regionInstanceGroupManagers`, `regionInstanceGroups`) spreads its VMs, each a zonal instance, over its `distributionPolicy.zones` (three of the region's when none are given): EVEN (the default; PROACTIVE redistribution), BALANCED and ANY spread alike here (every zone has the capacity), ANY_SINGLE_ZONE keeps them in one zone. Named ports are checked as Google documents (a name of the RFC 1035 rule, a port 1-65535, a stale fingerprint 412). Autoscalers and regional autoscalers scale on the VMs' real CPU, read every 15 seconds from each VM's cgroup (`cpu.stat`): recommended size = ceil(serving VMs × average utilization / target), VMs in their initialization period (`coolDownPeriodSec`) left out, clamped to the minimum and maximum, scaling out at once and in only to the highest recommendation of the last 10 minutes and as `scaleInControl` allows; mode OFF still recommends, ONLY_SCALE_OUT only adds. A zonal group's resize is overridden by its autoscaler at its next pass; an autoscaled regional group's resize is refused, as Google refuses it. The same readings are `compute.googleapis.com/instance/cpu/utilization` in Cloud Monitoring (gce_instance), sampled every 60 seconds. Predictive autoscaling, custom metric, load balancing and schedule signals answer 501 Rolling updates (`instanceGroupManagers.patch`, `regionInstanceGroupManagers.patch`, `applyUpdatesToInstances`, #2139), as compute/docs/instance-groups/rolling-out-updates-to-managed-instance-groups documents them: one version, or two for a canary (one with a fixed or percent `targetSize`, the other taking the rest); `updatePolicy.type` PROACTIVE replaces, restarts or refreshes every VM not on its version, a step at a time once the group's VMs are settled (every 2 seconds), within `maxSurge` and `maxUnavailable` (fixed or percent; by default 1 each in a zonal group and the number of zones in a regional one, whose fixed values must be 0 or at least that), OPPORTUNISTIC waits for `applyUpdatesToInstances` or a recreate; the action is the more disruptive of `minimalAction` and what the update needs (REFRESH in place when only the template's metadata differs, else REPLACE), never beyond `mostDisruptiveAllowedAction`; `replacementMethod` SUBSTITUTE makes VMs of new names, RECREATE keeps the names and needs `maxSurge` 0; `status.versionTarget.isReached` is false while a VM is on another template. |

| `startup-script` | Runs at every boot (`google-startup-scripts.service`), its output on the serial port as `google_metadata_script_runner` writes it |
| `ssh-keys` | The guest agent's account manager (a script polling every 2 seconds) makes each user, its `authorized_keys` and passwordless sudo (`google-sudoers`); project keys apply unless `block-project-ssh-keys` |
| Metadata server | The guest reads its instance and project attributes from the Compute port under a per-instance token (`CLOUDBURROW_GUEST_METADATA`); service account tokens come from the instance's metadata server, which `GCE_METADATA_HOST` names in the guest (in `/etc/environment` too). `metadata.google.internal` is not resolved in the guest |

| Serial port output | The container's console (`kubectl logs`), escape codes removed |
| stop / start, reset | The pod is deleted (the disks kept) and created again |
| suspend / resume | The container's cgroup is frozen on its kind node: memory and processes are kept |
| Disk budget | A new disk, instance or snapshot is refused with `RESOURCE_EXHAUSTED` (429) below 20 GiB free, as Kubernetes Engine refuses a node |

### VM networking and firewall rules

VMs on the same VPC network reach each other at their internal IPs, across the network's subnets, and at their internal DNS names; VMs on different networks cannot, unless the networks are peered: an `ACTIVE` peering (both sides made, #2140) puts the two networks' VMs on one data plane, each side's firewall rules still applied, and exchanges their subnet routes. The network's firewall rules are enforced on each VM as Google evaluates them (https://docs.cloud.google.com/firewall/docs/firewalls, read 2026-11-19), #1968:

| Google | Here |
|---|---|
| The VPC network's data plane | One VXLAN segment per network, inside the VMs' own network namespaces. Each guest has a `vpc0` VXLAN device whose VNI is derived from the network's ID, holding its internal IP (`/32`, MAC `42:01:` and the IP, as Google's guests see), an on-link route for each subnet range of the network, and a permanent neighbour and forwarding entry for each running peer on the network, whose packets travel to the peer's pod IP over the cluster's own network (UDP 4789). A VM of another network has another VNI and no forwarding entry, so nothing it sends arrives; overlapping ranges in two networks do not collide |
| Firewall rules | Compiled per VM into an nftables table (`inet cloudburrow`) the guest applies atomically, before its `vpc0` exists at boot: the rules that apply to the VM (no target, one of its network tags in `targetTags`, or its service account in `targetServiceAccounts`), by priority (the lowest number first), a deny before an allow of the same priority, then the implied rules: deny every other ingress, allow every other egress. Stateful (replies of an allowed connection pass, as on Google). Disabled rules are left out |
| Sources and destinations | An ingress rule's sources are the union of its `sourceRanges` and the primary internal IPs of the network's VMs that have one of its `sourceTags` or `sourceServiceAccounts`; `destinationRanges` (egress, and ingress when set) match the destination. Protocols `tcp`, `udp`, `sctp` (with ports), `icmp`, `esp`, `ah`, `ipip`, `all` and numbers |
| `default` network | Its `default-allow-internal` (`10.128.0.0/9`, every TCP and UDP port, ICMP), `-ssh`, `-rdp` and `-icmp` rules, at priority 65534, are enforced like any other |
| Internal DNS | `INSTANCE.ZONE.c.PROJECT.internal` (and the short name) of every VM on the network, in a managed block of the guest's `/etc/hosts`; as on Google, a VM of another network does not resolve them |
| Always allowed | The metadata server, and over the pod interface the cluster's own ranges (`10.244.0.0/16`, `10.96.0.0/12`: the guest's metadata and cluster DNS), are exempt from egress rules, as Google always allows `169.254.169.254` |

### Cloud Router and Cloud NAT

Routers (`compute.routers.*`, #2140) are served in the region they are made in, on a network of the project, many per region and network, as on Google (https://docs.cloud.google.com/network-connectivity/docs/router, https://docs.cloud.google.com/nat/docs/overview, read 2026-11-22):

| Google | Here |
|---|---|
| `bgp` | `asn` an RFC 6996 private ASN (64512-65534, 4200000000-4294967294) or 16550, else 400; `keepaliveInterval` 20 by default, 20 to 60; `advertisedGroups` (`ALL_SUBNETS`) and `advertisedIpRanges` only with `advertiseMode: CUSTOM`; `identifierRange` link-local, /30 or larger |
| `interfaces`, `bgpPeers` | An interface links at most one of a VPN tunnel, an Interconnect attachment or a subnetwork. Cloud VPN and Cloud Interconnect are not served, so the first two are refused 501; a subnetwork interface (a router appliance) is checked against the router's network and region, its `privateIpAddress` in the subnet. A peer names an interface, a `peerAsn`, and its addresses in the interface's range; Google's defaults: `advertisedRoutePriority` 100, `enable` `TRUE`, BFD `DISABLED` at 1000 ms and multiplier 5 |
| `getRouterStatus`, BGP sessions | A subnetwork interface's BGP peers (router appliances: `routerApplianceInstance` names a VM of the subnet's network directly, Network Connectivity Center not being served) get real sessions (#2140, `bgpspeakers.go`, `cmd/cloudburrow/computebgp.go`): a speaker pod on the network's VXLAN segment at the interface's `privateIpAddress` runs GoBGP's `gobgpd` (Apache-2.0, built once from its module at a pinned version, `dependencies.json`) with the router's ASN, each peer's `peerAsn`, keepalive (hold time three times it) and MD5 key, advertising each peer its routes (the network's subnets in the region, or every region with GLOBAL dynamic routing, or the custom groups and ranges) with its `advertisedRoutePriority` as MED. `getRouterStatus` shows each peer's real state, uptime and `numLearnedRoutes`, and `bestRoutes` and `bestRoutesForRouter` the learned prefixes with their next hop; the network's VMs in the region (every region with GLOBAL routing) route each learned prefix to the appliance, which must be a running VM with `canIpForward`; a prefix inside a subnet range is not taken. A peer is `DOWN` until its speaker reports. Docker Desktop's kernel has no TCP MD5, so an MD5-keyed session stays `DOWN` with `statusReason` `MD5_AUTH_INTERNAL_PROBLEM`. Each NAT gateway's addresses, its VMs and `minExtraNatIpsNeeded` |
| `nats[]` | `sourceSubnetworkIpRangesToNat` `ALL_SUBNETWORKS_ALL_IP_RANGES`, `ALL_SUBNETWORKS_ALL_PRIMARY_IP_RANGES` or `LIST_OF_SUBNETWORKS` (subnets of the router's region and network, `ALL_IP_RANGES`, `PRIMARY_IP_RANGE` or named secondary ranges); a subnet is translated by one gateway only, and a gateway of all subnets is its region and network's only one. `MANUAL_ONLY` takes reserved regional external addresses, which become `IN_USE` with the router as user (and `RESERVED` again when the gateway, or the router, goes); `AUTO_ONLY` is given an address of the local pool. Ports: 64 per VM by default (2 to 57344), 32 to 65536 in powers of 2 with dynamic port allocation, which Endpoint-Independent Mapping excludes. Endpoint-Independent Mapping is enforced (#2140): an internal IP:port leaves from one NAT port of the VM's range whatever the destination (a hash of the pair into the range), and a second internal port whose NAT port another flow to the same destination holds is dropped, Google's endpoint-independent conflict; without it each flow is given its own port. Dynamic port allocation gives each VM `minPortsPerVm` ports, doubles them when it holds 7/8 of them (up to `maxPortsPerVm`, at most 32768 in one block of an address), and halves them after 30 seconds at a quarter or less, each VM keeping its block while it is free; the five timeouts (UDP 30, ICMP 30, TCP established 1200, transitory 30, TIME_WAIT 120 seconds by default); `logConfig` (`ALL`, `ERRORS_ONLY`, `TRANSLATIONS_ONLY`); `rules` with `MANUAL_ONLY`. `type: PRIVATE` (Network Connectivity Center and hybrid spokes) is refused 501 |
| `getNatMappingInfo`, `getNatIpInfo` | Each translated VM (no external IP on its primary interface, on a subnet the gateway covers) given `minPortsPerVm` ports of a NAT IP from port 1024, as static allocation gives them, or its current dynamic allocation, exactly the ports its connections are translated to; each NAT IP `IN_USE` while it holds a VM's ports |
| Private NAT | `nats[].type` `PRIVATE` (#2140, nat/docs/private-nat, set-up-private-nat): the gateway translates its source subnets to the ranges of subnets of purpose `PRIVATE_NAT` in the router's network and region, named by its rules' `action.sourceNatActiveRanges` (and `sourceNatDrainRanges`); a rule's `match` names the next hop, `nexthop.hub == "//networkconnectivity.googleapis.com/projects/P/locations/global/hubs/H"`, `nexthop.is_hybrid`, or both joined by `\|\|`, optionally after `source.ip` conditions joined by `&&`, and every rule of a gateway has the same next hop (400 otherwise). A private gateway has no NAT IPs (`natIpAllocateOption`, `natIps` 400), no Endpoint-Independent Mapping, and dynamic port allocation by default; a subnet can have one public and one private gateway. Network Connectivity Center is not served, so a hub is checked for its form only, no hybrid or spoke traffic exists, and the gateway gives no internet egress and no mapping information |
| Route policies and named sets | `routers.updateRoutePolicy` (create or replace), `patchRoutePolicy` (merge), `getRoutePolicy?policy=`, `listRoutePolicies` (`compute#routersListRoutePolicies`), `deleteRoutePolicy?policy=`, and the same five for named sets (`namedSet=`, `NAMED_SET_TYPE_PREFIX` or `NAMED_SET_TYPE_COMMUNITY`, `elements[]`), as the REST references describe (read 2026-11-22): a name of RFC 1035, a type (`ROUTE_POLICY_TYPE_IMPORT` or `ROUTE_POLICY_TYPE_EXPORT`) that cannot change, terms of priority 0 to 2^31-1 unique in the policy (returned in priority order), each `match` and `actions[]` an `Expr` whose `expression` is checked for CEL syntax (balanced brackets, closed strings, no `=` assignment or `;`; 400) and kept as given; a `fingerprint` that changes on every write and, given, must match (412). A BGP peer's `importPolicies` and `exportPolicies` must name policies of that type (400), and a policy a peer uses cannot be deleted (400). No BGP session comes up, so no policy is applied to a route. A named set a route policy names (`prefixSets('NAME')`, `communitySets('NAME')`) cannot be deleted (400), as Manage named sets says. The Go client v1.62.0 has no named-set methods; they are served over REST. The console's Named sets tab makes, edits and deletes them |
| Internet egress | **A VM whose primary interface has no external IP reaches the internet only through a Cloud NAT gateway of its subnet**, as on Google: until one translates it, its guest's ruleset drops egress over its pod interface to every address outside RFC 1918 and 100.64.0.0/10 (`no external IP and no Cloud NAT`), whatever the egress rules allow. Private addresses stay reachable, so the VM still reaches this machine's CloudBurrow endpoints. Cloud NAT translates for real (#2140, `natgateways.go`, `cmd/cloudburrow/computenat.go`): each public gateway with VMs to translate runs a pod on the network's VXLAN segment at the subnet's gateway address; its VMs route `0.0.0.0/1` and `128.0.0.0/1` to it, and it translates TCP and UDP to the VM's NAT IP and port range that `getNatMappingInfo` reports, and ICMP to the NAT IP, under the gateway's UDP, ICMP, TCP established, transitory and TIME_WAIT timeouts; each kind node routes the NAT IPs back to the pod. `AUTO_ONLY` adds addresses as VMs need them; `MANUAL_ONLY` reports `minExtraNatIpsNeeded` and drops what it has no ports for. With `logConfig` enabled, new connections and drops are written to Cloud Logging as `compute.googleapis.com/nat_flows` on `nat_gateway` (`connection`, `allocation_status`, `gateway_identifiers`, `endpoint`, `vpc`), under the `ALL`, `ERRORS_ONLY` or `TRANSLATIONS_ONLY` filter. Leaving the cluster, the kind node masquerades the NAT IP to this machine's own address |

The routers' console pages are Network Connectivity's **Cloud Routers** (`/hybrid/routers/list`: Create router, a router's Router details, BGP sessions, Cloud NAT gateways and Interfaces, Edit, Delete) and Network services' **Cloud NAT** (`/net-services/nat/list`: Create Cloud NAT gateway with Google's sections, Create new router inline, Automatic or Manual addresses, Advanced configurations; a gateway's details, Allocated external IP addresses and Mapping information, Edit, Delete).

How it stays current: the guest's `cloudburrow-vpc.service` polls the Compute port every 2 seconds under its own token (`/cloudburrow/guest/TOKEN/cloudburrow/vpc`), reporting its pod IP and reading back its segment, peers, hosts and ruleset, and applies them when they change. A firewall rule inserted, patched or deleted, a VM's `setTags`, or a VM started or stopped takes effect on the other VMs within about 2 seconds (a stopped VM stops being a peer within 30).

Why this mechanism: it needs nothing on the kind nodes or in the CNI (kindnet), works across nodes, keeps each network's addresses off the pod network (so subnets may overlap the way they can on Google), and puts deny rules and priorities where NetworkPolicy cannot (it has neither). Its limits: ingress over the pod interface is dropped except the VXLAN underlay from the network's own peers, so a VM is not reachable around its firewall at its pod IP; but the guest runs as root in a privileged container, so a guest's own root can remove its own rules (its own ingress and egress only: it cannot change another VM's). SSH from this machine reaches the guest through the forwarded port on its loopback, not the VPC, so it is not subject to the rules (on Google, SSH to the external IP needs a rule such as `default-allow-ssh`). Firewall logging, hierarchical and network firewall policies, and secure tags are not enforced; a subnet range overlapping the cluster's `10.244.0.0/16` or `10.96.0.0/12` is not reachable from VMs.

As `TestComputeVMNetworkingThroughTheGoClient` does with the Go client: a custom network with rules allowing TCP 8080, 8081 and 7070 at 1000, denying 8081 from the subnet at 900, allowing 9090 from the `client` tag to the `server` tag and denying the `client`'s egress to 7070, then VMs `server` and `client` on it; from `client`, `nc -z SERVER_IP 8080` connects, 8081 (the deny at 900 wins), 8082 (no rule: the implied deny) and 7070 (its egress deny) do not, 9090 does; `SERVER.us-central1-a.c.PROJECT.internal` resolves; a VM on `default` reaches another on `default` on any port (`default-allow-internal`) and reaches neither of them.

Every mutation answers a zonal operation (global for snapshots) that is `RUNNING` while the backend works and `DONE` (with its error when it failed) after; `zoneOperations.wait` waits for it. A resource's operations run one after another, in the order they were asked for: a `stop` asked while an `attachDisk` is still restarting the VM's container runs once the attach is done, and the instance ends `TERMINATED` (#2052).

### Serverless VPC Access

Serverless VPC Access (`vpcaccess.googleapis.com` v1, #2140) is served on the Compute Engine port, JSON under `/v1/projects/P/locations/R/`: `connectors` create, get, list, patch and delete, their operations and the locations. `patch` (in the v1 discovery document, not in the proto the `apiv1` client binds, so served over JSON only: `google.golang.org/api/vpcaccess/v1`'s `Connectors.Patch` or gcloud's `connectors update`) changes `machineType`, `minInstances` and `maxInstances` only, the counts only upwards ("Decreasing the number of instances for existing connectors is not supported"), the minimum below the maximum and the maximum at most 10; any other field in `updateMask` is refused 400. A network or subnet a connector uses cannot be deleted (`resourceInUseByAnotherResource`), as a Cloud Router's network cannot. Its gRPC API is served on the same port too (#2160). Use the REST transport of the official client, or its gRPC transport with insecure transport credentials (`vpcaccess.NewRESTClient` with `option.WithEndpoint("http://" + computeAddr)`); there is no gRPC listener. A connector needs a network and an unused /28 `ipCidrRange` of the private ranges, or an existing /28 `subnet` that nothing else uses; `minInstances` 2 to 9, `maxInstances` 3 to 10, the machine type `e2-micro`, `f1-micro` or `e2-standard-4`. It is `READY` at once. The console's VPC network menu has **Serverless VPC access** with Create connector, and Edit on a connector.

Cloud Run services and jobs then name a connector in `template.vpcAccess.connector` (or a bare connector ID, expanded), or use Direct VPC egress (`networkInterfaces` with a network and subnet of the region), each checked as Google checks it and recorded on the service and its revisions; the Run console's Networking tab shows and edits them.

Their traffic is carried (#2140, `internal/service/compute/gateways.go`, `cmd/cloudburrow/computerunegress.go`). Each connector, and each Direct VPC egress setting (subnet and network tags), in use by a running revision or task gets a gateway: a pod on the network's VXLAN segment, running the VM image's own VPC agent, at an address of the network: the second of the connector's `/28` (or of its subnet), as Google's connector instances take theirs from it, or a free address of Direct VPC egress's subnet, kept from VMs. Every few seconds the kind nodes' policy routing sends what each such pod sends to the network's subnet ranges (its ACTIVE peers' and connectors' too) to its gateway, which forwards it onto the network with its own address as the source. A connector in a project's own network makes Google's six firewall rules in it, `aet-REGION-NAME-hcfw`, `-rsgfw`, `-earfw`, `-egrfw`, `-sbntfw` (its range into the network) and `-tagfw` (its instances' tag `vpc-connector-REGION-NAME`, which its gateway carries), listed and enforced like any rule and deleted with it (vpc/docs/serverless-vpc-access, read 2026-11-22). So the VMs' ingress firewall rules decide on the connector's range or the subnet address, and Direct VPC egress's network tags match `sourceTags`, as on Google. Internal load balancers' and endpoints' addresses are carried from the gateway as from a VM (`vpcservices.go`). With `ALL_TRAFFIC`, everything but the cluster's ranges and this machine also goes through the gateway, which lets it out only while a Cloud NAT gateway covers its subnet. A pod without `vpcAccess` has no route to a network's internal addresses. As `TestRunReachesVMsThroughConnectorsAndDirectVPCEgress2140` does: a VM serving port 80, a connector on `default`, and Cloud Run services with the connector, with Direct VPC egress on `default` and with neither: the first two fetch the VM's page at its internal IP; the third cannot.

### SSH

The guest's port 22 is forwarded to a loopback port, named in `instances.get` and the aggregated list as `cloudburrowSshAddress` (and in the console's Connect column). The instance's `natIP` is its own unrouted `192.0.2.0/24` address (see [External IP addresses](#external-ip-addresses)), not the forwarded port's host.

**gcloud compute ssh always dials port 22 of the natIP**: it has no port flag of its own, and the port cannot be put in the instance's address. Pass the forwarded port, and `127.0.0.1` in place of the natIP, to its `ssh` with `--ssh-flag` (the console's Connect shows this command):

```sh
PORT=$(curl -s http://127.0.0.1:COMPUTE_PORT/compute/v1/projects/PROJECT/zones/us-central1-a/instances/vm-1 | jq -r .cloudburrowSshAddress | cut -d: -f2)
gcloud compute ssh vm-1 --zone us-central1-a --ssh-flag="-p $PORT" --ssh-flag="-o HostName=127.0.0.1" --strict-host-key-checking=no
```

gcloud makes its key (`~/.ssh/google_compute_engine`, or `--ssh-key-file`) and adds it to the project's `ssh-keys` metadata (`projects.setCommonInstanceMetadata`); the guest applies it within seconds. `--strict-host-key-checking=no` is needed because the host key gcloud records is per instance ID, and guest attributes (`hostkeys/`) are not served. `TestGcloudComputeInstances` runs exactly this, with `HOME` and the key in throwaway directories. `--internal-ip`, `--tunnel-through-iap` and OS Login are not served.

Plain `ssh` works the same with any key in `ssh-keys`:

```sh
ssh -p PORT -i KEY USER@127.0.0.1
```

### External IP addresses

As Google documents (vpc/docs/reserve-static-external-ip-address, compute/docs/ip-addresses/configure-static-external-ip-address, read 2026-11-22), #2140:

| Google | Here |
|---|---|
| Ephemeral external IP | An access config without `natIP` gets a distinct address of its own from `192.0.2.0/24`, recorded on the access config; it is a record, not a route (nothing outside the VPC data plane reaches a VM; SSH uses `cloudburrowSshAddress`) |
| Promote an ephemeral IP to static | `addresses.insert` in the VM's region with `address` set to its `natIP`: the address keeps the IP, is `IN_USE` with `users` the instance, of the access config's `networkTier`; another region, or a different tier, is refused |
| Assign a static external IP | `accessConfigs[].natIP` of a `RESERVED` regional `EXTERNAL` address of the VM's region, at insert or with `instances.addAccessConfig` (after `deleteAccessConfig`); one `IN_USE` or of another region is refused; the tier is the address's |
| Release | `addresses.delete` is refused while `IN_USE`; deleting the VM, or `deleteAccessConfig`, returns the address to `RESERVED` |
| A given external address (BYOIP) | 501: no address here is the project's own |

The console's IP addresses page lists each VM's ephemeral external address with Promote to static IP address, the static ones with In use by, and Reserve external static IP address's Attached to assigns the new address to a VM of its region.

### Regional disks

As Google documents (compute/docs/disks/regional-persistent-disk, high-availability-regional-persistent-disk and the `regionDisks` reference, read 2026-11-22), #2139: `regionDisks` insert, get, list, delete, resize, setLabels, createSnapshot and add/removeResourcePolicies, and `regionDiskTypes` get and list.

| Google | Here |
|---|---|
| `replicaZones` | Exactly two distinct zones of the disk's region, or 400 |
| Types and sizes | `pd-balanced` and `pd-ssd` from 10 GB, `pd-standard` from 200 GB, to 65,536 GB; other types (`pd-extreme`, Hyperdisk) are refused for a regional disk |
| Attaching | `instances.insert` and `attachDisk` with `source` `regions/REGION/disks/NAME`, from a VM of either replica zone; a VM of another zone is refused |
| Synchronous replication | The region's zones are one cluster here, so a regional disk is **one** storage volume (a PersistentVolumeClaim) that the VMs of both replica zones mount: every write lands on the one copy, so the replicas are always in sync. A zone outage, and so failover (force-attach, `stopAsyncReplication`), is not simulated |
| Snapshots | `createSnapshot` stores the snapshot in the disk's region; a regional or zonal disk can be made from it |

The console's Create a disk takes Location type Single zone or Regional, with the Replica zone; the Disks list shows a regional disk's two zones, and Attach existing disk on a VM of either zone offers it.

### IPv6

As Google documents (vpc/docs/subnets#ipv6-ranges, create-modify-vpc-networks#ipv6, compute/docs/ip-addresses/configure-ipv6-address, read 2026-11-22), #2140:

| Google | Here |
|---|---|
| ULA internal IPv6 (`enableUlaInternalIpv6`) | The network gets a `/48` of `fd20::/20` as `internalIpv6Range`, or the one given (in `fd20::/20`, not another network's); turning it off is refused while a subnet uses it |
| Dual-stack subnet (`stackType: IPV4_IPV6`) | `ipv6AccessType` `INTERNAL` takes a `/64` of the network's ULA range (`internalIpv6Prefix`), `EXTERNAL` a `/64` of `2600:1900::/28` (`externalIpv6Prefix`); `ipv6CidrRange` is that range. An IPv4-only subnet can be patched to dual-stack, and back while no interface uses IPv6; the access type does not change. `IPV6_ONLY` is 501 |
| Dual-stack VM | A `stackType: IPV4_IPV6` interface on a dual-stack subnet gets a `/96` of the subnet's `/64`: `ipv6Address` with `internalIpv6PrefixLength: 96` (internal), or an `ipv6AccessConfigs` entry `DIRECT_IPV6` with `externalIpv6` (external, Premium tier); an address asked for is a reserved static one of the subnet or a free one of its range; on an IPv4-only subnet it is refused |
| Reachability | The address is on the guest's `vpc0` (`/128`, no DAD) with an on-link route for each IPv6 range of the network (and of a network peered with `stackType: IPV4_IPV6`), and a permanent neighbour for each running dual-stack peer: IPv6 frames ride the network's VXLAN segment, which runs over the cluster's IPv4 underlay, so the kind cluster (IPv4 only, kindnet) need not be dual-stack. External IPv6 addresses are carried between the network's VMs, not routed off the cluster |
| Firewall rules | IPv6 ranges in `sourceRanges` and `destinationRanges` are compiled to `ip6` matches, IPv4 ones to `ip`, so one rule may hold both; a source tag or service account matches the VMs' IPv6 addresses too |
| Static IPv6 addresses | `addresses.insert` with `ipVersion: IPV6` in a region: `INTERNAL` of a dual-stack subnet with internal IPv6, `EXTERNAL` (Premium) of one with external IPv6, a `/96` of its range, given or chosen; a VM takes it as its interface's `ipv6Address` (or `ipv6AccessConfigs[].externalIpv6`), `IN_USE` until the VM goes. A global IPv6 address (load balancers) is 501 |
| IPv6 static routes | `routes.insert` with an IPv6 `destRange` outside the subnets' IPv6 ranges, its next hop the default internet gateway, an IPv6 address of a dual-stack subnet of the network (`nextHopIp`), or a dual-stack instance of it; an IPv4 next hop, or an IPv4-only instance, refused. Recorded and listed as IPv4 static routes are; like them, not applied in the guests |
| IPv6-only subnet (`stackType: IPV6_ONLY`) | `ipv6AccessType` `INTERNAL` or `EXTERNAL`, holding only its `/64`: no IPv4 range, gateway, secondary ranges or expansion, no stack-type change either way, none on an auto mode network (#2140) |
| IPv6-only VM (interface `stackType: IPV6_ONLY`) | On an IPv6-only or dual-stack subnet, Debian or Ubuntu images only (as Google allows), a `/96` and no `networkIP` or IPv4 access config; it reaches the network's IPv6-only and dual-stack VMs over the VXLAN segment by address and by internal DNS name, and still reaches the metadata server and CloudBurrow over its pod |
| Global IPv6 addresses | `globalAddresses.insert` `ipVersion` `IPV6` gives an external Premium `/64` of `2600:1901::/32` (no address may be given; internal is refused, as on Google); a global external forwarding rule takes `ipVersion` `IPV6` (or infers it from its address) and is served on its listener on this machine like every rule. A regional rule with `ipVersion` `IPV6` (#2140; an internal passthrough or managed load balancer, or a backend service-based external passthrough one, Premium Tier; a target pool is IPv4 only) names its `subnetwork`, a dual-stack or IPv6-only one whose IPv6 access type is the rule's (`INTERNAL` or `EXTERNAL`), and is given a `/96` of its range (or the reserved regional IPv6 address named), its `IPAddress` in Google's `ADDRESS/96` form; it is served on its listener, and VMs of the network reach an internal one at its address through their guest's `relay6` (nftables cannot rewrite an IPv6 destination to the IPv4 listener), the egress firewall rules applying to the address |
| External IPv6 | Carried only inside the VPC: kind's pod network is IPv4 only and Docker Desktop routes no public IPv6 (the kind Docker network has a ULA, `fc00:f853:ccd:e793::/64`, that no pod has), so an external IPv6 address cannot reach the internet or be reached from it |

The console's Create VPC network has ULA internal IPv6, its allocation and the range; a subnet's IP stack type and IPv6 access type; Edit subnet's IP stack type (IPv4 to dual-stack and back); Reserve internal static IP address's IPv6; Create an instance's network interface IP stack type and External IPv4 address (Ephemeral, None or a reserved address of the region); the Subnets list's IP stack type, Internal and External IPv6 ranges columns; a VM's network interfaces list its IPv6 addresses; firewall rules take IPv6 source and destination ranges.

### Terraform

`google_compute_instance`, `google_compute_disk` and `google_compute_attached_disk` apply, plan clean and destroy through `cloudburrow terraform` (`TestTerraformComputeInstance`). With `google_compute_attached_disk`, put `lifecycle { ignore_changes = [attached_disk] }` on the instance, as Google's provider documentation says.

Clean up with `instances delete` (the boot disk is deleted with it); a stopped CloudBurrow keeps the pods, and `cloudburrow delete` removes the cluster with them. The images it built stay in Docker until removed (`docker images 'cloudburrow-vm-*'`).
