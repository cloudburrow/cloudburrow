# Support matrix

This file is the authoritative statement of what CloudBurrow supports.

**Three separate things are tracked separately**, because conflating them is how a tool
over-promises:

| Dimension | Question | Where |
|---|---|---|
| **GCP API compatibility** | Does an official Google SDK call behave correctly? | §Services below |
| **Native Kubernetes portability** | Do ordinary manifests, Helm charts and operators work? | §Native Kubernetes |
| **Knative feature coverage** | Which Cloud Run v2 behaviors does the adapter actually map? | §Cloud Run |

A component being adopted from upstream does not make its operations supported. **Upstream
behavior still has to be demonstrated through an official SDK** before it is promoted here. It is not a roadmap
and not an aspiration. If an operation is not listed as `Verified` here, CloudBurrow does not
support it, regardless of what any other document, README, or commit message says.

## Status values

| Status | Meaning |
|---|---|
| `Planned` | Not implemented. May return `UNIMPLEMENTED`, or may not be routed at all. |
| `Partial` | Implemented with documented gaps. The gap is named in the Notes column; an unexplained `Partial` is a documentation bug. |
| `Verified` | Implemented **and** exercised by a merged test that drives it through an official Google client library. |
| `UNVERIFIED` (an error code) | The call is Verified, but an error code the test asserts is one **Google does not document**. It is implemented as the most plausible code and marked `// unverified:` in the test, so [docs/coverage](coverage/README.md) lists it and a row that relies on it says `(error code UNVERIFIED)`. It stays so until a recorded observation pins it; see [test/compat/README.md](../test/compat/README.md#unverified-error-codes). |

**The promotion rule.** An operation moves off `Planned` only in a PR that adds a test using
an official Google SDK — `cloud.google.com/go/...`, `google-cloud-*` for Python, and so on.
A curl invocation, a handwritten HTTP request, or an internal unit test is not sufficient
evidence, because those test our understanding of the API rather than the client's.

**Control plane vs data plane.** These are tracked separately because they fail
independently, and conflating them is the standard way an emulator overstates itself.
Creating a Cloud Run service and receiving a well-formed `Service` response says nothing
about whether a container ran. A service is described as supported only when both columns are
`Verified`.

**Backing component** is recorded per service, from the
[upstream reuse audit](upstream-evaluation.md). Inherited limitations are listed with the
service — an upstream gap is still our gap as far as a user is concerned.

**Verified** rows below are backed by `test/compat`, run against a live `cloudburrow up` on
2026-09-20. Everything else remains `Planned`: exercised-by-hand is not evidence, and an
operation a test merely touches in cleanup is not asserted.

#### Retried once

CI retries five tests once, and no others (#566). When `go test` fails in a compat shard or in
the restart probe and every test it names as failed is on this list, those tests are re-run once,
by name, with the same environment, and the run fails if a retry fails too. A failure of any
other test fails at once, and so does a package-level failure that names no test (#675). A pass
on the second attempt counts as a pass, so the rows that cite these tests say that their evidence
tolerates one retry. Every retry is a `::warning::` annotation on the run page and a line of the
job summary with its outcome (#704).

|---|---|---|
| `TestHostEndpointSurvivesABackendRestart` | Compat shard | Advertised host port after a pod restart |
| `TestMemorystoreAcrossRestart` | Restart probe | Memorystore durability |
| `TestDatastoreAcrossRestart` | Restart probe | Datastore keeps its data in persistent mode |
| `TestDatastoreSurvivesAPodRestart` | Compat shard | Datastore keeps its data in persistent mode |
| `TestSpannerStateDoesNotSurviveARestart` | Compat shard | Spanner state does not survive a restart |

**Removal rule.** An entry is taken off the list once 20 consecutive CI runs on `main` have
passed with no retry of it, counted from the annotations. A test is added only together with a

allow-list in `.github/scripts/retry-flaky.sh` differ.

## Cloud Storage — JSON API v1

**Backing component:** CloudBurrow's own server (`internal/service/storage`, #485), built to
Google's documentation and the storage v1 discovery document, which it embeds: every method of
that document is either served or answers **501 `notImplemented` naming it**. It is the only
Cloud Storage backend (#519). `up` runs it as one Deployment, from an image built locally from
the binary embedded in the CLI (#514); `cloudburrow storage-server` runs it with no cluster.
Contract: Cloud Storage JSON API v1, and the XML API subset below.
Client endpoint override: `STORAGE_EMULATOR_HOST` (Go, Python; see architecture §4.2). The Node
client needs `apiEndpoint` instead (see [Node.js client libraries](#nodejs-client-libraries)).

The per-method status is generated from the server's own method table in
[docs/coverage/storage.md](coverage/storage.md): a method is **Verified** when an official-SDK
or real-tool compat test annotated for it passes, **Implemented** when it is served but no such
test covers it, and **Unimplemented** when it answers 501. `TestCoverageMatchesCompatibility`
fails if a row below disagrees with that report. The official Go client retries every 5xx, 501
included, until its deadline, so an unimplemented method costs a client its timeout rather than
failing at once.

### What the server does

Built to Google's spec in steps (#485), one issue per feature:

#### Buckets (#490)

Are served: insert, get, list (prefix, pages of at most 1000), patch as a JSON merge patch (an omitted field stays, `null` clears it, a `null` label removes that key), update, delete, and metageneration with `ifMetagenerationMatch`/`NotMatch` (412 `conditionNotMet`; 304 for a read). Every settable field is kept, stored or refused by name with 400, never dropped with 200; see the bucket fields table below. A non-empty bucket delete is 409 (UNVERIFIED for the JSON API).

#### Objects (#491)

Media and multipart uploads (`uploadType=media`, `multipart`; a metadata-only POST is 400 `wrongUrlForUpload`), with `Content-MD5`, `x-goog-hash` and the metadata's `md5Hash`/`crc32c` verified and a mismatch refused; `ifGenerationMatch` (including 0, "only if absent") and the other three preconditions; metadata reads, `alt=media`, `/download/storage/v1/…`, and XML `GET`/`HEAD /{bucket}/{object}` with the `x-goog-*` headers; one byte range (`a-b`, `a-`, `-N`; 206, or 416 with `Content-Range: bytes */size`); and a new generation, metageneration 1, on every finalize. `TestStorageObjectRoundTrip`, `TestStorageChecksums` and `TestMultipartUploadStoresMetadataWithContent` pass against it.

#### Object metadata (#492)

Patch (merge; a `null` metadata key removes it) and update (replace), each advancing the metageneration and keeping the generation and bytes; `customTime` only moves forward and cannot be removed, as documented; A body may restate the object's `storageClass` but not change it, which only a rewrite does (#515); holds and retention follow the retention rules below. Preconditions combine with AND on the live generation unless one is named: `ifGeneration(Not)Match`, `ifMetageneration(Not)Match` (412, or 304 for a failed NotMatch on a read), `If-Match` (412) and `If-None-Match` (304 on reads), and for the XML API `x-goog-if-generation-match`, `x-goog-if-metageneration-match`, `If-Modified-Since` (304) and `If-Unmodified-Since` (412). `TestStorageGenerationPreconditions` and `TestObjectMetadataUpdate` pass against it.

#### Listing (#494)

`prefix`, `delimiter` with synthetic `prefixes` (which count toward `maxResults`), `includeTrailingDelimiter`, `startOffset`/`endOffset`, `matchGlob` (`**`, `*`, `?`, `[…]`, `[!…]`, `{a,b}`), and pages of at most 1000 in byte order. `TestStorageListWithPrefix` passes against it.

#### Resumable uploads (#493)

A session from `uploadType=resumable` (200 with `Location`; the `upload_id` is random), chunks by PUT or POST with `Content-Range: bytes a-b/TOTAL|*` (every chunk but the last a multiple of 256 KiB; persisted bytes immutable, so a re-sent range is skipped), and an incomplete chunk answered **308 with `Range: bytes=0-N`**, or, with `X-GUploader-No-308: yes` as the Go client sends it, **200 with `X-Http-Status-Code-Override: 308`**. Both handshakes are undocumented and required by the clients. `bytes */TOTAL` and `bytes */*` query the status; the final chunk verifies `x-goog-hash` and applies `X-Goog-Meta-*`; DELETE cancels with 499. A session lasts a week, then answers 410 for a week, then 404. Sessions and their chunks survive a restart in persistent mode. `TestStorageResumableUploadAndRangedRead` and `TestResumableUploadCompletes` pass against it.

#### Compose, copy, rewrite and move (#495)

Compose takes 1 to 32 sources of one storage class, with per-source `generation` and `ifGenerationMatch` and `deleteSourceObjects`; the result has **no MD5**, a CRC32C combined from the components, and `componentCount` (counting a composite's components). Copy and rewrite share the source's bytes, cross buckets and honour `ifSource*`; rewrite changes the storage class, and with `maxBytesRewrittenPerCall` (a multiple of 1 MiB) proceeds by tokens, each good for a week and once. Move renames atomically within a bucket. `kmsKeyName`, `dropContextGroups` and the destination ACL and key parameters are refused by name. `TestStorageCompose`, `TestStorageCopy` and `TestObjectCopyAndRewrite` pass against it; the Go client's copier sends `objects.rewrite`, so `TestStorageObjectsCopy` drives `objects.copy` through Google's generated JSON API client, and `TestStorageObjectMove` drives `objects.move` through the Go client's `ObjectHandle.Move`.

#### Batch (#496)

`POST /batch/storage/v1` takes a `multipart/mixed` body of `application/http` parts, dispatches each through the same handler as the direct call, and answers each in order with `Content-ID: <response-…>`; an upload or a download inside a batch is refused per part, and more than 100 calls refuse the whole batch (the refusal is UNVERIFIED). A part's body needs no `Content-Length`: the Python client sends none, and the body is the rest of the part.

#### Object versioning (#498)

On a bucket with `versioning.enabled`, replacing or deleting the live version keeps it as a **noncurrent** version with its generation and a `timeDeleted`; noncurrent versions appear only with `versions=true` (each name's oldest first, paged within a name) or when named by `generation=`, and can be read, patched and used as a copy source. A delete that names a generation removes that version permanently. Disabling versioning stops new noncurrent versions and keeps the existing ones, `ifGenerationMatch=0` succeeds when only noncurrent versions exist, and a bucket holding only noncurrent versions is not empty (409). Versions survive a restart in persistent mode. `TestStorageVersioningKeepsNoncurrent`, `TestStorageVersioningDeleteKeepsNoncurrent`, `TestStorageVersioningDisableKeepsExisting`, `TestStorageDoesNotExistWithOnlyNoncurrent` and the restart probe `TestStorageVersioningPersistentMode` pass against it.

#### Soft delete (#499)

Every bucket has a soft delete policy, 7 days unless set (7 to 90 days, or 0 for none; `effectiveTime` moves when the retention changes). Under it, a version that leaves the bucket (deleted, overwritten, or a deleted noncurrent version) is kept **soft-deleted** with `softDeleteTime` and `hardDeleteTime`: hidden from reads and listings, listed with `softDeleted=true`, its metadata readable by generation (never its bytes), and `objects.restore` makes it live again as a new generation with metageneration 1, retiring any live version it replaces. A restore answers **412 `softDeletePolicyNotSet`** on a bucket without a policy and **412 `objectNotSoftDeleted`** for a live or noncurrent generation, as the status-codes page lists. A bucket whose only objects are soft-deleted can be deleted; it is then soft-deleted itself under its own policy, readable and listable with `softDeleted=true`, and `buckets.restore` brings it back empty, with its soft-deleted objects restorable again (a live bucket of the same name refuses the restore with 409, UNVERIFIED). A policy change applies only to later deletions. Reads treat anything past its `hardDeleteTime` as gone, and a sweep removes it. A move is a rename and leaves nothing soft-deleted (UNVERIFIED). `bulkRestore` is 501. `TestStorageSoftDeleteAndRestore`, `TestStorageRestoreNotSoftDeleted412`, `TestStorageRestoreWithoutPolicy412`, `TestStorageBucketDeleteIgnoresSoftDeleted` and `TestStorageBucketsRestore` pass against it.

#### Retention and holds (#500)

With the status-codes page's reasons: a bucket `retentionPolicy` (1 s to 3,155,760,000 s) applies to existing and new objects, which report `retentionExpirationTime`; an object younger than the period cannot be deleted or replaced (**403 `retentionPolicyNotMet`**), though a versioned bucket may make it noncurrent, and its metadata stays editable. `lockRetentionPolicy` needs `ifMetagenerationMatch` (required in the pinned discovery document; 400 without, 412 stale) and a policy (400 `badRequest`). **A second lock of a locked policy is refused 400 `badRequest`** "The retention policy on bucket … is already locked." and changes nothing, metageneration included (#829). This is UNVERIFIED: the lockRetentionPolicy reference, the bucket-lock and using-bucket-lock pages and the status-codes page say what a lock needs and that it is irreversible, but not what a repeat lock answers, and no observation of Google has been recorded; 400 `badRequest` is the status-codes page's reason for a lock the bucket's settings do not allow, the conservative choice over accepting it. The metageneration is checked first, so a stale one is 412 whether or not the policy is locked; a locked period can grow but not shrink or be removed (400 `badRequestException`; the discovery document says PERMISSION_DENIED, the status-codes page 400). `temporaryHold` and `eventBasedHold` block delete and replace (**403 `objectUnderActiveHold`**) but not metadata changes; releasing an event-based hold restarts the retention clock, and no `retentionExpirationTime` is given while it is held; `defaultEventBasedHold` holds each new object. Object retention `{mode, retainUntilTime}` needs a bucket created with `enableObjectRetention=true` (400 `invalid` otherwise, and with an event-based hold); removing, shortening or locking an Unlocked one needs `overrideUnlockedRetention=true` (403 `forbidden`), and a Locked one only extends. A copy, rewrite or restore does not inherit holds or retention. Holds also block a live version becoming noncurrent (UNVERIFIED). `TestStorageRetentionBlocksDelete`, `TestStorageLockRetentionPolicy`, `TestStorageLockRetentionPolicyTwice`, `TestStorageHoldsBlockDelete` and `TestStorageObjectRetentionRequiresEnabledBucket` pass against it.

#### Lifecycle (#501)

`lifecycle.rule` is validated when set, and an unknown action or condition is 400 naming it, with the old configuration kept. Actions are Delete, SetStorageClass and AbortIncompleteMultipartUpload (#508; with only `age`, `matchesPrefix` and `matchesSuffix`, as documented). Conditions are `age`, `createdBefore`, `customTimeBefore`, `daysSinceCustomTime`, `daysSinceNoncurrentTime`, `isLive`, `matchesPrefix`/`matchesSuffix` (at most 1000 across all rules), `matchesStorageClass`, `noncurrentTimeBefore`, `numNewerVersions` and `sizeAboveBytes`/`sizeBelowBytes` (at most 5 TiB). The rules run at least hourly on the server's clock, and on demand with `POST /_cloudburrow/lifecycle`. A rule's conditions combine with AND; `age` 0 is met at midnight UTC after creation, and age N N days after it. Delete takes precedence over SetStorageClass, and the cheapest target class wins; a class only moves to a cheaper one. A hold or an unmet retention period keeps Delete from taking effect, and a deleted live version becomes noncurrent or soft-deleted as any delete does. No limit on the number of rules is imposed, since none is documented. `TestStorageLifecycleConfigRoundTrip` and `TestStorageLifecycleUnknownCondition400` pass against it.

#### CORS (#502)

**CloudBurrow checks the browser's origin first** (#677, [ADR-0004](adr/0004-local-access-and-no-authentication.md)). Google can allow any origin because every call carries an OAuth token; CloudBurrow checks none, so a page on any site you have open could otherwise read and change every bucket. A request with an `Origin` header is served only when the origin is loopback (`http://` or `https://` at `127.0.0.1`, `[::1]`, `localhost` or `*.localhost`, any port), the server's own, or named with `up --cors-allow-origin` ([configuration.md](configuration.md#browser-access-to-cloud-storage)). Any other origin, `https://evil.example` say, gets **403 with no CORS headers**, a preflight included, however the bucket's `cors` is set. A request with no `Origin` (the SDKs, `gcloud`, `curl`) is not checked. This is a deliberate difference from Google. `TestStorageCORSRefusesForeignOrigin`, `TestStorageCORSLoopbackOriginWorks` and `TestStorageCORSAllowlistedOriginWorks` pass against it, the last two with a resumable upload started and finished from the browser's origin.

For an origin that passes, Google's behaviour applies. The bucket's `cors` (`origin`, with `*`; `method`; `responseHeader`; `maxAgeSeconds`, 3600 by default) is kept and validated. **XML endpoints** follow it: a preflight is answered from the first rule that matches its origin, its method and every requested header, with that rule's methods and max age; a preflight that matches none gets **200 with no CORS headers**, as documented; an actual request that matches gets `Access-Control-Allow-Origin` and the rule's `responseHeader` as `Access-Control-Expose-Headers`. **JSON endpoints** (`/storage/v1`, uploads, downloads, batch) always allow, whatever the bucket says: the Origin echoed, `DELETE, GET, HEAD, PATCH, POST, PUT`, a Max-Age of 3600, and the requested headers echoed (UNVERIFIED). **`Access-Control-Allow-Credentials` is not sent.** It was sent on simple requests until #677, but no recorded observation of Google shows it: the storage oracle compares against storage-testbench, which records no CORS behaviour, and Google was never called. CloudBurrow reads no cookies, so dropping it loses nothing a page could use. A resumable session URI answers with the Origin that started the session, and is itself behind the origin check. `TestStorageCORSRoundTrip`, `TestStorageXMLPreflightMatches`, `TestStorageXMLPreflightMismatch200NoHeaders` and `TestStorageJSONAlwaysAllowsCORS` pass against it.

#### XML API subset (#507)

Path-style or virtual-hosted (`{bucket}.{host}` with `storage-server --host`): object `PUT` (with `x-goog-meta-*`, `Cache-Control` and the other content headers, `x-goog-storage-class`, `x-goog-if-generation-match`/`-metageneration-match` and `Content-MD5`; 200 with the ETag, `x-goog-generation` and `x-goog-hash`, no body), `GET`/`HEAD` (#491) and `DELETE` (204); bucket `GET` (a `ListBucketResult` with `prefix`, `delimiter` and its `CommonPrefixes`, `marker`, `max-keys`, `IsTruncated` and `NextMarker`) and `DELETE`; and resumable uploads, where `POST` with `x-goog-resumable: start` is **201 with the session URI**, chunks are `PUT` to it with `Content-Range` (308 while incomplete), and a `DELETE` cancels with **204**. Errors are `<Error>` documents: `NoSuchBucket`, `NoSuchKey`, `PreconditionFailed`, `BucketNotEmpty` (409), `InvalidArgument`, `InvalidRange`, `AccessDenied`. `x-goog-copy-source`, `x-goog-acl` and customer encryption headers are refused by name; bucket `PUT`, service `GET` and form `POST` are 501. Signed URLs (#509) are verified; see the data plane. `TestStorageXMLPutGetDelete`, `TestStorageXMLListBucket`, `TestStorageXMLResumable201And204`, `TestStorageXMLErrorCodes` and `TestStorageXMLHostStyle` pass against it.

#### XML multipart uploads (#508)

`POST ?uploads` (an `InitiateMultipartUploadResult` in the S3 namespace the clients parse), `PUT ?partNumber=N&uploadId=` for N 1 to 10,000 (the ETag, and `x-goog-hash` the Python client validates; the same number again replaces the part), `POST ?uploadId=` with `CompleteMultipartUpload` (parts in ascending order with their ETags; every part but the last at least 5 MiB; **no MD5** on the object, as documented, and a CRC32C), `DELETE ?uploadId=` (**204**), list parts (`max-parts`, `part-number-marker`, at most 1000) and `GET /{bucket}?uploads`. **Preconditions are refused with 400 `NotImplemented`**, as the docs say they are not supported. The codes for a part out of order, a bad ETag or a small part are S3's `InvalidPartOrder`, `InvalidPart` and `EntityTooSmall`, and the completed upload's ETag is S3's `"md5-of-md5s-N"`; all UNVERIFIED. An incomplete upload stays until aborted, or until a lifecycle `AbortIncompleteMultipartUpload` rule (age, `matchesPrefix`, `matchesSuffix`) removes it. Google's Python `transfer_manager.upload_chunks_concurrently` uploads a 20 MiB file in 5 MiB parts against it: `test_transfer_manager_xml_multipart_upload` runs in CI (#516). `TestStorageXMLMultipartAbort204`, `TestStorageXMLMultipartListParts` and `TestStorageXMLMultipartPreconditionRefused` pass against it.

#### Persistence by mode (#512; the #481 lesson)

With `--data-dir`, `storage-server --mode persistent` (the default) keeps buckets, every object version's bytes and metadata, and in-progress resumable sessions across a restart. `--mode ephemeral` deletes the store an earlier run left in that directory before serving, so nothing survives whatever is on disk: the choice is made by the mode, never by whether a store exists. CI's restart probe `TestStorageAcrossRestart` runs at setup, after a persistent restart (a bucket, a two-version object and a 256 KiB-in session: **present**; with a Pub/Sub emulator, a notificationConfig too, #701) and after an ephemeral restart on the same directory (**absent**); unit `TestStorageEphemeralClearsLeftoverStore` does the same in-process. `up` passes the instance's mode to the in-cluster server (#514), and the compat job's restart probe measures it on every merge (#596): the same `TestStorageAcrossRestart` runs against the in-cluster server through the instance's tunnel at setup, after `stop` and `up` (**present**, from the Deployment's PVC) and after `up --mode ephemeral` (**absent**; the Deployment has no volume). The session is resumed at the restarted instance's endpoint, whose port is OS-assigned and so new.

#### In the cluster (#514)

`up` runs **one** Deployment for the host and the cluster, with no notification front, no second Deployment and no Host-binding workaround (#268), because the server builds `mediaLink` from each request's Host. Its image is built at `up` from the Linux `cloudburrow-storage` binary embedded in the CLI, on a distroless base pinned by digest (`build.storageServerBase`), and `kind load`ed; nothing is published or downloaded but the base. Readiness is a real request (`GET /storage/v1/b?project=_`). A NetworkPolicy allows egress only to DNS and the Pub/Sub emulator; kind's default CNI does not enforce NetworkPolicy, so `TestStorageNoEgress` proves in-process that a whole workload resolves no name at all. Measured against a real instance: 58 builtin storage and notification compat tests passed through the tunnel, the e2e `TestAcceptanceWorkflow` passed with the worker's `STORAGE_ENDPOINT` on the single Deployment, and the CLI scrapes the server's calls into `/admin/events` and `/metrics`. Measured for #514: a pod could **not** reach the CLI's loopback-bound ports through the kind gateway, but **could** through `host.docker.internal` on Docker Desktop, admin API included (#553). **The official Go client retries every 5xx, 501 included, until its deadline**, so a method not built yet costs a client its timeout rather than failing at once. CI runs the whole compat suite against it twice: through the tunnel on an instance (the `official SDK compatibility (storage)` shard, #565), and against a standalone `cloudburrow storage-server` with the Python suite, the restart probes and a registered signing certificate (`check` job).

#### Official clients and tools (#516, #517)

**The official Python client** (google-cloud-storage 3.14.1, #516) runs against the storage server in CI: CRUD with a resumable upload, a resume after an interrupted chunk (`recover()`'s `bytes */*` answered 308 with the `Range` held), `mediaLink` on the emulator's host, `if_generation_match=0` and a ranged download, batch, `transfer_manager` XML multipart, and a V4 signed URL. **gcloud storage** (586.0.0, #517; CI installs that release, checksum-pinned, #694), configured by `gcloud-setup` alone, with every non-loopback request refused by a test proxy: `storage ls`, `buckets create`, `buckets update --update-labels` then `--clear-labels`, `objects update`, `hmac create/list/update/delete`, and `cp` of 200 MiB by the parallel composite path. ### UNVERIFIED choices

Where no Google page states a behaviour, the server makes a choice and marks it UNVERIFIED in the
test that pins it; the method-level codes are also listed in [docs/coverage/storage.md](coverage/storage.md).

- `buckets.delete` of a non-empty bucket answers 409, as the XML API documents `BucketNotEmpty`; no page states the JSON API's status.
- `buckets.setIamPolicy` with a stale etag answers 412, the JSON API's precondition code.
- A live bucket of the same name refuses `buckets.restore` with 409.
- A move is a rename and leaves nothing soft-deleted; holds block a live version becoming noncurrent.
- More than 100 calls refuse a whole batch.
- The JSON API's CORS defaults beyond `Allow-Origin`, `Allow-Methods` and `Max-Age`: the requested headers echoed. (`Allow-Credentials` is no longer sent, #677.)
- XML multipart part order, ETag and size errors use S3's `InvalidPartOrder`, `InvalidPart` and `EntityTooSmall`, and the completed upload's ETag is S3's `"md5-of-md5s-N"`.
- A signed URL's `X-Goog-Expires` is at most 604800 seconds, from the docs rather than a measured refusal.

## Pub/Sub — `google.pubsub.v1`

**Backing component:** Google `cloud-pubsub-emulator` 0.8.35 (integrate).
Contract: `google/pubsub/v1/pubsub.proto`. Client endpoint override: `PUBSUB_EMULATOR_HOST`.

**Inherited limitations**, measured in #24:

- **State is not persisted.** A topic was `NotFound` after restart even with `--data-dir`.
  Pub/Sub is effectively memory-only, and CloudBurrow will not imply otherwise.
- **IAM methods return `Unimplemented`.** The emulator announces this at startup.
- The emulator describes itself as a "fake" that "may be incomplete or differ from the real
  system."

**CloudBurrow's front** (#873). The emulator stores a subscription's `expiration_policy` and never
acts on it, so the Pub/Sub pod runs `cloudburrow-storage pubsub-front` (`internal/pubsubfront`)
beside it, on the Service's port, from the locally built storage image; the emulator listens on
the pod's port 8086, which the Service does not publish. Every client goes through the front, the
host tunnel, workloads in the cluster and the storage server's notifications alike, and it passes
every call through unchanged except the ones the Subscription expiration row names. **It serves
the emulator's REST API too**, as the emulator does, on the same port: a connection that opens with
the HTTP/2 preface is gRPC, and any other is HTTP/1.1, proxied to the emulator's REST API with the
same rules (checks and the 31-day default on `PUT .../subscriptions/{s}`, the retention check on
`PATCH`, and every call on `.../subscriptions/{s}` or `{s}:verb`, and a snapshot's create, as
activity), so gcloud and Terraform's google provider, which use REST, work as before
(`TestGcloudPubSub`, `TestPubSubRESTSubscriptionExpiresWhenIdle`, `TestGcloudSetupConfiguration`,
`TestTerraformSchedulerAndSubscription`). A REST client speaking plain-text HTTP/2 with prior
knowledge would reach the gRPC side and be refused; none of those clients does. The
[subscription properties page](https://cloud.google.com/pubsub/docs/subscription-properties) and
`Subscription.expiration_policy` in `google/pubsub/v1/pubsub.proto` are the rules it follows: a
subscription is active while a subscriber is "issuing operations on the subscription", "Examples of
subscriber activities include open connections, active pulls, or successful pushes", the default
ttl is 31 days, the minimum 1 day, a policy without a ttl never expires, and a ttl "must be at
least as long as the message retention duration". Neither source names a maximum, so none is
enforced. A second method on the same port, `cloudburrow.pubsub.v1.EmulatorClock/Advance`
(a `google.protobuf.Duration` in, the front's time out), moves the front's clock forward, so tests
pass a day in a moment instead of using a ttl Google refuses. It is not part of the Pub/Sub API,
and it grants nothing a caller could not already do, since the emulator has no authentication and
anyone who reaches the port can delete a subscription. Because the front runs from the storage
image, a Pub/Sub instance now needs a CLI with the embedded Linux binaries (`make build` or a
release), as Cloud Storage already did.

Since #880 the front also relays the emulator's pushes, refuses exactly-once delivery on a push or
export subscription (see the Exactly-once delivery row), and answers three more CloudBurrow
methods, for `cloudburrow state save` and `load`: `cloudburrow.pubsub.v1.SubscriptionActivity/Export`
and `/Import` read and set how long each subscription has been idle (a `google.protobuf.Struct` of
seconds by subscription name), and `cloudburrow.pubsub.v1.Projects/List` names every project a call
through the front has named (a `google.protobuf.ListValue`), since the emulator serves any project
and cannot list them. **The push relay:** the front hands the emulator, for every push
subscription, an endpoint of its own on the pod's loopback (port 8087) that carries the
subscription and the real endpoint, and puts the real endpoint back in every subscription the
emulator returns (`CreateSubscription`, `GetSubscription`, `UpdateSubscription`,
`ListSubscriptions`), so no client sees the relay's. Each push is forwarded to the real endpoint
with its method, headers and body, and the endpoint's status, headers and body are the emulator's
answer; one Google counts as a success (102, 200, 201, 202 or 204, from
[the push page](https://cloud.google.com/pubsub/docs/push)) is activity on the subscription. An
endpoint the relay cannot reach is a 502 to the emulator, which retries it as it would any failed
push.

Since #891 the front also applies an `UpdateSubscription` of `expiration_policy`, which the
emulator refuses ("Updating the expiration_policy field is currently unsupported in the Pub/Sub
Emulator"). It takes the path out of the mask the emulator sees and forwards the rest; an update of
that path alone never reaches the emulator. The new ttl is checked by the same rules as on create
(at least 1 day, and no shorter than the message retention, the new one when the same update
changes it), then kept in the front, which puts it in every subscription it returns
(`GetSubscription`, `ListSubscriptions`, `UpdateSubscription`) and enforces it in place of the
emulator's stored policy. A `CreateSubscription` or `DeleteSubscription` of the name, or the
subscription's expiry, drops it. An update that names the path with no policy is read as a
subscription created without one: Google's 31-day default (CloudBurrow's reading; the API reference
does not say). `state save` reads through the front, so it saves the updated policy, and `state load`
creates the subscription with it, which the emulator then keeps (unit
`TestPubSubStateKeepsAnUpdatedExpiration`). The kept policies are lost if the front's container
restarts alone. **Over REST too** (#908): a `PATCH .../subscriptions/{s}` whose `updateMask` names
`expirationPolicy` (what `gcloud pubsub subscriptions update --expiration-period` sends) is
checked the same way, the path is taken out of the mask and the subscription the emulator is sent,
a PATCH of that path alone is answered by the front, and the kept policy is in every REST read
(`PUT`, `GET`, `PATCH .../subscriptions/{s}`, `GET .../subscriptions`); a `PUT` of the name drops
it. `TestGcloudPubSubUpdateExpiration`: `--expiration-period=12h` is refused; 3d and `never` are
applied, read back by `describe`, `list`, REST `GET` and the gRPC client, and enforced (with a
1-day ttl raised to 3 days, kept 25 hours on and gone once idle for 73; never, kept), and a plain
REST PATCH of the policy with the ack deadline applies both (unit
`TestRESTPatchSetsTheExpirationPolicy`, `TestRESTUpdateChecksThePolicy`).

**REST clients get the same** (#908). A push endpoint sent over REST, in `PUT
.../subscriptions/{s}` (`pushConfig.pushEndpoint`), in a `PATCH` whose `updateMask` names
`pushConfig`, or in `POST .../subscriptions/{s}:modifyPushConfig`, reaches the emulator as the
relay's, and the answers to `PUT`, `GET` and `PATCH .../subscriptions/{s}` and `GET
.../subscriptions` name the real one, with every other field of the JSON as the emulator sent it.
Exactly-once delivery with a push endpoint or an export is refused 400 `INVALID_ARGUMENT` on `PUT`,
`PATCH` and `:modifyPushConfig`, by the same checks as gRPC. Every `/v1/projects/{p}/...` path
records its project for `Projects/List`, so `cloudburrow state save` captures a project only
gcloud or Terraform used. `TestGcloudPubSubPushSubscription`: of four push subscriptions gcloud
makes with a 1-day ttl, the three given a storage-server upload endpoint by `subscriptions create
--push-endpoint`, `subscriptions update --push-endpoint` and `modify-push-config` are kept 25 hours
on with pushes at 0 and 20, and the one whose endpoint refuses its pushes is gone; `describe`,
`list` and the gRPC client read each real endpoint. `TestGcloudPubSubRefusesExactlyOnceWithPush`
and `TestPubSubRESTPushAndExactlyOnce` (plain REST, including a BigQuery export and an endpoint set
over gRPC read back over REST) assert the refusals and the reads. `TestGcloudPubSubStateSave`: a
project only gcloud used is saved, reset and loaded, and gcloud describes its subscriptions as they
were. Unit `TestRESTPushEndpointsGoToTheRelay`, `TestRESTReadsNameTheRealEndpoint`,
`TestRESTRefusesExactlyOnceWithPush`, `TestRESTProjectsAreListed`.

### Cloud Run: Jobs and executions

`google.cloud.run.v2.Jobs` and `google.cloud.run.v2.Executions` are served on the Cloud Run port
over gRPC (#582). A job is configuration, stored as a ConfigMap the adapter owns
(`run-job-<id>`, labelled `cloudburrow.dev/owned=true`, the job kept as protojson); each
`RunJob` creates one `batch/v1` Job, which is the execution. Its containers are rendered by
**the same code as a service's revision**: image localisation and pull policy, untagged images
refused, `command`, `args`, `workingDir`, `env`, `secretKeyRef` resolved to the Secret Manager
store's Kubernetes Secret, and `resources.limits`. They are served over JSON too, on the same port (#591): Terraform's
`google_cloud_run_v2_job` applies, updates and destroys (`TestTerraformRun`). `gcloud run jobs`
uses Cloud Run's v1 API, which is not served. Instances, Tasks, Builds and WorkerPools are not
registered.

For Spanner this is now **measured rather than quoted**: `TestSpannerStateDoesNotSurviveARestart`
writes a row, restarts the pod, waits for the endpoint to come back, and reads —

```
after the restart the data is gone: spanner: code = "NotFound",
desc = "Instance not found: projects/.../instances/cb-durab"
```

The test fails rather than passes if the endpoint does not return, because an unreachable
address is not evidence about durability. It is on CI's [retry-once list](#retried-once), so this
evidence tolerates one retry.

**Datastore keeps its data in persistent mode, measured (#307).** In persistent mode the
emulator's on-disk store is on a PersistentVolumeClaim, and the emulator's JVM is the container's
main process. The Cloud SDK emulator writes its store only when it shuts down cleanly, and both
`gcloud beta emulators datastore start` and the `cloud_datastore_emulator` script run the JVM as
a child that never receives the pod's SIGTERM, so under the wrapper an entity written before a
pod restart was lost. In ephemeral mode it runs through the wrapper with `--no-store-on-disk`,
as it always did. `TestDatastoreSurvivesAPodRestart` writes an entity with the Go client,
deletes the pod, and reads every entity written so far back from the new one, three times over.

started. CI's restart probe reads a probe entity after `stop` and `up` in persistent mode, and
finds none after `up --mode ephemeral` (`TestDatastoreAcrossRestart`). Both tests are on CI's
[retry-once list](#retried-once), so this evidence tolerates one retry. `status` reports `volume` for Datastore, and for every
other service, only in persistent mode. Firestore and Bigtable are still documented from Google's description,
not measured.

**Guards.** `guard.mjs` is loaded with `--import` into every process of the run. It refuses to
start unless `GOOGLE_APPLICATION_CREDENTIALS` is unset or is the generated fixture, and it checks
that application default credentials resolve to that fixture (exit 3). Every TCP connection and
every DNS lookup must be loopback. Node's gRPC (`@grpc/grpc-js`) is JavaScript and connects
through `net` like the HTTP clients do, so, unlike the Python guard, this one sees the gRPC
sockets as well as the HTTP ones. A violation makes the process exit 4, and so fails the run, even
if the test that caused it caught the error. `guard.test.mjs` proves both guards by running
sessions that break them. Each service's tests skip when `cloudburrow env` exports no variable for
that service.

### Host endpoints survive a backend restart

| Capability | Status | Notes |
|---|---|---|
| Advertised host port after a pod restart | **Verified** | `TestHostEndpointSurvivesABackendRestart` restarts the pod and requires the printed address to both accept a connection **and carry a request**; this evidence tolerates one retry, since the test is on CI's [retry-once list](#retried-once). Each tunnel binds a pod the forwarder chooses itself: the newest one that is Ready and **not being deleted**. `kubectl port-forward svc/…` could bind a pod that was terminating but still Ready during a rollout, such as `up --mode ephemeral` replacing a persistent pod, and connections through it hung (#381). |

This was broken until the restart criterion exposed it: the forwarder started `kubectl
port-forward` once and watched nothing, so a crash, an OOM kill, an eviction or a rollout left
the advertised endpoint dead for the life of the instance, while the pod was `Running`, the
service existed, and the startup banner still printed the address. Worse than a refusal: the
port still **accepted connections** and carried nothing, so a client's `connect()` succeeded
and every request timed out.

The tunnel is supervised and re-established on the **same** host port — the address has
already been printed, may be in an application's configuration, and for storage is baked into
the backend's advertised download URL, so reconnecting elsewhere would be a different kind of
broken. `Restarts()` counts re-establishments, because surviving a restart and never noticing
one are different states.

**Why it still flaked in CI (#526), measured:** `kubectl port-forward` does **not** exit when
its pod is deleted while the tunnel is idle. It keeps listening, fails the *next* connection's
stream, and exits only then. A supervisor that watched only for the process exiting therefore
kept a dead tunnel until a client tripped over it, and on a loaded runner the relaunch that
followed could bind the Service, resolving to whichever pod kubectl found, Ready or not.
Three failed CI runs showed the shape: the emulator up within a second of the restart, every
forwarder reporting its process alive, and clients timing out for minutes reading a server
preface that never came. Now the supervisor **watches the bound pod** and replaces the tunnel
within seconds of the pod going, **binds only a Ready, non-terminating pod** when it
re-establishes (never the Service), and counts a tunnel as up only once a probe connection
through it is **carried**, not merely accepted, using kubectl's own stream errors as the
signal. Each exit and re-establishment is logged, so a diagnose bundle says what the tunnel
did. In-process: `TestATunnelWhosePodIsGoneIsReplacedWithoutAClient`,
`TestRelaunchWaitsForAReadyPodInsteadOfTheService`, `TestALaunchWhoseStreamFailsIsRetried`,
against a fake kubectl.

**The filter grammar ListLogEntries accepts:**

```
filter = term { [ "AND" ] term }
term   = field op value
field  = logName | severity | resource.type | timestamp
op     = "=" | "!=" | ">" | ">=" | "<" | "<="   (logName and resource.type take = and != only)
value  = a bare word, or a double-quoted string
```

Terms are ANDed, and an explicit `AND` is optional. `severity` compares by level:
`DEFAULT < DEBUG < INFO < NOTICE < WARNING < ERROR < CRITICAL < ALERT < EMERGENCY`.
`timestamp` values are RFC 3339. Everything else is refused with INVALID_ARGUMENT naming the
term: `OR`, `NOT`, parentheses, the `:` has-operator, functions, and any other field such as
`jsonPayload.*`, `labels.*` or `textPayload`. `logadmin` appends its own
`timestamp >= "…"` term, which this grammar accepts.

**Built, not reused** (#309): Google publishes no Cloud KMS emulator, and each third-party one departs from Google's documented behaviour ([upstream-evaluation.md](upstream-evaluation.md#amendment-cloud-kms-is-built-not-reused-309)).

**One port serves gRPC and JSON** (#414), as `cloudkms.googleapis.com` does: an HTTP/2 request with an `application/grpc` content type goes to gRPC, and everything else goes to the JSON router, the shared `Transcoder` in `internal/transport/rest` (#591), which calls the same registered gRPC server. ## Cloud Storage — notifications to Pub/Sub

The storage server serves `notificationConfigs` and **detects the events itself** (#506).
Every event is written to an outbox in the same transaction as the mutation that caused it; a
dispatcher then publishes it to the Pub/Sub emulator after commit and deletes it once
published, retrying a failed publish (up to 20 attempts, so a topic that never exists cannot
hold the queue forever), so an event is never lost between the mutation and the publish. In an
instance the emulator is the cluster's Pub/Sub; `storage-server --pubsub-emulator host:port`
names one, and without one, creating a configuration is 501.

## Fault injection — `/admin/faults`

Rules on the loopback-only control port (#306) make calls to the services CloudBurrow serves
itself fail or slow down: Cloud Tasks, Secret Manager, the Cloud Run adapter, Cloud KMS
(#392, `TestKMSFaultInjectionAgainstTheSDKRetry`), Cloud Scheduler, Cloud Logging and Resource
Manager (#600, `TestFaultsSchedulerLoggingAndResourceManager`). That lets a
client's retry and deadline handling be exercised with the SDK it actually uses. A service is
fault-injectable exactly when `up` has wired the fault interceptor into its server: building the
interceptor is what makes its rules accepted, so there is no separate list to fall out of step, and
a rule for a service that is not enabled is refused rather than accepted and never applied.

```sh
curl -X POST http://<control>/admin/faults -d '{"service":"secretmanager","method":"AccessSecretVersion","code":"UNAVAILABLE","count":2}'
curl http://<control>/admin/faults              # list, with each rule's injected and remaining counts
curl -X DELETE http://<control>/admin/faults    # all rules; ?id=fault-1 for one
```

| Field | Meaning |
|---|---|
| `service` | `tasks`, `secretmanager`, `run`, `kms`, `scheduler`, `logging` or `resourcemanager` when enabled, and `storage` where its server runs in the same process (#513); required. A refusal names the services this instance accepts |
| `method` | a glob over the method name, `AccessSecretVersion` or `Get*`; default every method |
| `project` | only calls whose resource is under `projects/{project}` |
| `probability` | 0 to 1, default 1 |
| `code` or `httpStatus` | the gRPC code by name, or an HTTP status mapped to its code as Google maps them; default `UNAVAILABLE` |

**Visual fidelity and API compatibility are separate claims with separate evidence**, and
neither implies the other. A screen that renders correctly proves nothing about the API
behind it, and a verified API proves nothing about the screen.
