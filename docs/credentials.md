# Credentials and the local metadata server

> **CloudBurrow authenticates nothing.** Every adapter serves every caller. What follows
> exists so that tools which *insist* on having credentials — `gcloud`, Terraform, the Google
> SDKs — can be run offline against a local instance. A token minted here is accepted because
> CloudBurrow accepts everything, not because it was verified.

## `cloudburrow env`

```sh
eval "$(cloudburrow env)"
```

prints, and exports, everything a Google client needs:

```
export CLOUDSDK_API_ENDPOINT_OVERRIDES_PUBSUB="http://127.0.0.1:9002/"
export CLOUDSDK_API_ENDPOINT_OVERRIDES_STORAGE="http://127.0.0.1:9001/storage/v1/"
export CLOUDSDK_CORE_PROJECT="cloudburrow"
export GCE_METADATA_HOST="127.0.0.1:9005"
export GOOGLE_APPLICATION_CREDENTIALS="~/.cloudburrow/cloudburrow/credentials.json"
export GOOGLE_CLOUD_PROJECT="cloudburrow"
export PUBSUB_EMULATOR_HOST="127.0.0.1:9002"
export STORAGE_EMULATOR_HOST="http://127.0.0.1:9001"
```

`--format json` and `--format plain` are available for scripting. It takes the same
configuration flags as `up`, so it reports the endpoints of the instance you actually
started.

### Why this matters more than convenience

Google's libraries find credentials automatically. **If you do not export the fixture, they
find your real ones.** Measured, on a machine with an ordinary `gcloud auth login`:

```
$ go run ./adcprobe                    # no GOOGLE_APPLICATION_CREDENTIALS
project from ADC:
token type=Bearer value=ya29.a0AdMD6... valid=true      # ← a real Google token

$ GOOGLE_APPLICATION_CREDENTIALS=<fixture> go run ./adcprobe
project from ADC: p86
token type=Bearer value=cbl_e7fcxxEo... valid=true      # ← local, no egress
```

The first run **reached Google over the network** to refresh a real token. Running
`cloudburrow env` is what keeps a local development loop local.

## The credentials fixture

`credentials.json` is written into the instance state directory on first `up`, beside the
kubeconfig. It is an ordinary `service_account` ADC file, with one difference: **every URL in
it points at CloudBurrow.**

```json
{
  "type": "service_account",
  "project_id": "cloudburrow",
  "client_email": "cloudburrow-local@cloudburrow.iam.gserviceaccount.com",
  "token_uri": "http://127.0.0.1:9005/token",
  "auth_provider_x509_cert_url": "http://127.0.0.1:9005/certs",
  "private_key": "-----BEGIN PRIVATE KEY-----...",
  "_cloudburrow": "Generated by CloudBurrow for local development. This key authorises
     nothing: it is accepted only by a local CloudBurrow instance, which performs no
     authentication at all."
}
```

A Google client reads it, signs a JWT assertion with the key, and POSTs that assertion to
`token_uri` — which is CloudBurrow. It gets a `cbl_…` token back. Nothing leaves the machine.

The RSA key is **generated once and persisted** (`credentials-key.pem`, mode `0600`). A key
that changed on every `up` would invalidate any client that had already read the file, and
the resulting "invalid signature" points nowhere useful.

The `_cloudburrow` field is not part of the format. It is there so that anyone who opens the
file — or finds it in a repository by accident — sees immediately that it grants nothing.

## The metadata server

A GCE metadata server on `127.0.0.1:9005` (`--port-metadata`), for clients that look for one
rather than for an ADC file.

| Path | Answer |
|---|---|
| `/` | `computeMetadata/` — the probe a client uses to decide it is "on GCE" |
| `/computeMetadata/v1/project/project-id` | the instance's project |
| `/computeMetadata/v1/instance/zone` | `projects/<n>/zones/us-central1-a`, fully qualified |
| `.../service-accounts/` | `default/` and the account's email |
| `.../service-accounts/default/token` | `{"access_token":"cbl_…","expires_in":3600,"token_type":"Bearer"}` |
| `.../service-accounts/default/identity?audience=…` | an RS256 JWT |
| `.../service-accounts/default/email`, `/aliases`, `/scopes` | as Google returns them |
| `/certs` | the JWKS for the instance's signing key |

Point clients at it with `GCE_METADATA_HOST`.

**`Metadata-Flavor: Google` is required**, and set on every response including refusals.
Google's server requires it so that a web page cannot read tokens from `169.254.169.254` with
a plain cross-origin request. CloudBurrow enforces it even though its tokens grant nothing:
a local server that accepted what a real one rejects would teach code to work here and fail
in production.

## What these tokens are not

| | |
|---|---|
| **Access tokens** | Opaque `cbl_…` strings, as they are opaque on Google. Deliberately **not** JWTs: making one look verifiable invites someone to try to verify it. |
| **ID tokens** | Real RS256 JWTs, signed with the instance's own key and verifiable against `/certs`. They will **not** verify against Google's public certificates, because Google did not issue them. |
| **Validation** | None, anywhere. CloudBurrow never checks a token, an assertion, a signature or an expiry. The token endpoint checks only that an assertion was *sent*, so a client silently sending none finds out. |
| **Authorization** | None. There is no IAM, no scopes enforcement, no per-resource permission. Every caller can do everything. |

## Verified with real tooling

**`gcloud storage`** — the bucket list came from CloudBurrow:

```
$ export CLOUDSDK_API_ENDPOINT_OVERRIDES_STORAGE="http://127.0.0.1:8462/storage/v1/"
$ export CLOUDSDK_AUTH_ACCESS_TOKEN=$(curl -sH 'Metadata-Flavor: Google' \
    http://127.0.0.1:9005/computeMetadata/v1/instance/service-accounts/default/token | jq -r .access_token)
$ gcloud storage ls
gs://cb-e2e-21250000-bucket/
gs://cb-env-bucket/
```

**`gcloud pubsub`**:

```
$ gcloud pubsub topics create cb-env-topic
Created topic [projects/p86/topics/cb-env-topic].
$ gcloud pubsub topics list
name: projects/p86/topics/cb-env-topic
```

**Terraform**, full create/read/destroy against the `hashicorp/google` provider:

```
$ terraform apply -auto-approve
google_pubsub_topic.tf: Creation complete after 0s [id=projects/p86/topics/cb-terraform-topic]
google_storage_bucket.tf: Creation complete after 0s [id=cb-terraform-bucket]
Apply complete! Resources: 2 added, 0 changed, 0 destroyed.

$ terraform destroy -auto-approve
Destroy complete! Resources: 2 destroyed.
```

with:

```hcl
provider "google" {
  project      = "p86"
  access_token = var.access_token
  storage_custom_endpoint = "http://127.0.0.1:8462/storage/v1/"
  pubsub_custom_endpoint  = "http://127.0.0.1:8463/v1/"
}
```

`terraform init` downloads the provider plugin once, which is a real network request. Every
operation after that is local.

### `gcloud` ignores the emulator variables

**A finding worth knowing.** `STORAGE_EMULATOR_HOST` and `PUBSUB_EMULATOR_HOST` are read by
the Google *client libraries*, **not by `gcloud`**. With only those set, `gcloud` goes to the
real service:

```
$ PUBSUB_EMULATOR_HOST=127.0.0.1:8463 gcloud pubsub topics list
ERROR: (gcloud.pubsub.topics.list) UNAUTHENTICATED: Request had invalid authentication
credentials. ... service: pubsub.googleapis.com
```

That request left the machine. `gcloud` needs `CLOUDSDK_API_ENDPOINT_OVERRIDES_*`, which is
why `cloudburrow env` exports both sets rather than choosing one.

## If you want to point a pod at this

The metadata server binds loopback, so it is reachable from your machine and not from inside
the cluster. Pods reaching a metadata server is not supported today — see
[compatibility.md](compatibility.md).
